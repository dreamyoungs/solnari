# Codex conversation privacy

Solnari's Codex integration is designed for temporary, in-memory conversations. Database
metadata and query results can contain sensitive business information, so conversation
persistence must be an explicit future opt-in rather than a default.

This document governs the future in-app Codex conversation. The separately implemented local MCP
server for external agents is opt-in, has no conversation store, and exposes only bounded tools for
the connection currently selected in Solnari. See [MCP access](mcp-access.ko.md).

## App Server contract

When starting a Codex App Server thread, Solnari must send `ephemeral: true`:

```json
{
  "method": "thread/start",
  "params": {
    "ephemeral": true
  }
}
```

The client must reject or terminate a session unless the returned thread reports both:

- `ephemeral` as `true`; and
- `path` as `null`.

Solnari must not use a persisted thread as a fallback when ephemeral thread creation fails.
Closing the assistant session or terminating the application discards the in-memory
conversation.

## Local data handling

Solnari must not write any of the following to files, databases, preferences, analytics,
telemetry, or crash reports:

- user prompts or assistant responses;
- SQL text sent to or generated by Codex;
- schema descriptions, query results, or tool payloads;
- database credentials, connection strings, tokens, or private hostnames.

Operational logs may contain content-free metadata such as request identifiers, durations,
status codes, and error categories. Debug logging of App Server standard input and output must
remain disabled in production builds. Error messages shown to users must be redacted before
they enter any diagnostic channel.

The live transcript may exist only in process memory while its assistant session is open.
Solnari must not restore it after relaunch and must not call persistence-oriented thread APIs
for that transcript.

## Context minimization

The integration should send the smallest useful context. Prefer selected schema metadata over
sample rows, and require an explicit user action before including result data. Secret fields
must be excluded at the model-context boundary even when they are visible elsewhere in the
application.

## Verification requirements

Backend integration is not complete until automated tests demonstrate that:

1. every new assistant thread requests ephemeral mode;
2. a non-ephemeral or path-backed response fails closed;
3. prompts, responses, SQL, schema data, and result values never reach application logs;
4. closing a session removes its in-memory transcript; and
5. relaunching Solnari cannot restore a prior assistant conversation.

This contract governs Solnari's local persistence behavior. It does not by itself alter the
data-retention policy of the selected model provider or account; those controls must be
reviewed separately when the backend is implemented.
